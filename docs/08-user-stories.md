| US-02 | 業務主管 | 身為業務主管，我希望覆核或退回公司料號、客戶料號、對應關係及價格，以便只讓確認過的資料投入交易。 |

| US-04 | 業務主管 | 身為業務主管，我希望 SO 核准後才預留庫存並開放缺料採購與出貨，以免未成立需求占用庫存或提前採購。 |
| US-05 | 採購 | 身為採購，我希望把已核准 SO 尚待規劃的缺料建立為關聯 PO 草稿，或依安全庫存建立一般補庫 PO，以便處理訂單需求與日常補貨。 |
| US-06 | 採購主管 | 身為採購主管，我希望 PO 核准後才產生正式 PDF、形成採購在途並向供應商下單，以便控管採購承諾。 |
| US-07 | 倉管 | 身為倉管，我希望依 PO 記錄合格、損壞與規格不符數量，使系統只將合格數量計入庫存，並讓關聯 PO 的合格數量補足來源 SO。 |
| US-08 | 業務 | 身為業務，我希望在 SO 已核准且預計出貨量均已預留後通知出貨並建立 DO 草稿，以便倉管依交貨安排履約。 |
| US-09 | 倉管 | 身為倉管，我希望依 DO 完成揀貨、包裝，確認不高於預計量的實際出貨量並產生正式出貨單 PDF，使 DO 進入等待交車的 `READY` 狀態，以確保貨物與文件一致。 |
| US-10 | 倉管 | 身為倉管，我希望在貨物與文件交給司機時執行出貨過帳，以便正式移出庫存、鎖定 DO 並留下操作紀錄。 |
| US-11 | 財務 | 身為財務，我希望核對每張已過帳 DO 自動產生的應收草稿，填入外部發票資料並確認正式應收，以便追蹤收款且避免重複請款。 |
| US-12 | 業務 | 身為業務，我希望申請取消尚未出貨的剩餘數量，以便主管核准後釋放預留，並把取消金額計入實際核准期間。 |
| US-13 | 系統管理員 | 身為系統管理員，我希望替其他員工指派多個角色或角色以外的個別額外權限並保留紀錄，同時禁止任何人修改自己的授權，以因應兼任及擴編並降低自行提升權限的風險。 |
| US-14 | 業務 | 身為具權限的業務，我希望完成本人 LINE 綁定，以一則完整自然語言需求取得 Structured Output 預覽，並在確認後建立 SO 草稿，以減少人工輸入又保有最後確認。 |
| US-15 | 營運主管 | 身為營運主管，我希望比較淨接單與營收趨勢，並依客戶、商品及未出貨訂單狀態查看變化來源，以便決定優先處理的營運問題。 |
| US-16 | 營運主管／採購主管 | 身為主管，我希望查看缺貨風險、可用庫存、已規劃未下單、採購在途、平均日出貨量、可支撐天數、平均採購週期、建議安全庫存及來源依據，以便決定補貨、催辦採購、協調交期或分批出貨。 |
| US-17 | 業務主管 | 身為業務主管，我希望查看交易降溫客戶及其歷史交易變化，以便安排業務確認原因與後續聯繫。 |
| US-18 | 營運主管 | 身為營運主管，我希望取得附有來源資料的 AI 營運摘要，以便快速掌握重要異常、可能原因及建議處理順序。 |
| US-19 | 財務 | 身為財務，我希望系統依 `DUE_0`、`NET_30` 或 `NET_60`，以 DO 實際出貨日計算到期日，以便用一致規則管理應收。 |
| US-20 | 業務／採購／倉管 | 身為交易承辦人，我希望系統把銷售或採購單位換算成庫存基準單位，以便入庫、預留與出庫數量保持一致。 |
| US-21 | 營運主管 | 身為營運主管，我希望在原核准人是資料建立者或本輪送審者時，以相應權限替代核准客戶、SO、供應商或 PO，以落實建立者與送審者都不得自行核准的規則。 |
| US-22 | 財務主管 | 身為財務主管，我希望直接設定客戶的 `DUE_0`、`NET_30` 或 `NET_60`，並保存修改前後值與原因，以便簡化流程又保留授信責任與追溯紀錄。 |
| US-23 | 採購 | 身為採購，我希望區分 SO 缺料中哪些已有 PO 規劃、哪些已成為正式在途、哪些仍無供應來源，以便避免重複採購並正確追蹤供應進度。 |
| US-24 | 倉管主管 | 身為倉管主管，我希望以具原因且可追溯的庫存調整處理未被預留的盤點差異，並在調減會侵蝕預留時由系統拒絕操作，以便避免破壞既有訂單承諾。 |
| US-25 | 採購主管 | 身為採購主管，我希望能取消尚未收貨的已核准 PO，或將部分收貨的 PO 短收結案，以便正確移除不再到貨的採購在途並讓來源 SO 重新規劃供應。 |
| US-26 | 倉管主管 | 身為倉管主管，我希望在公司料號尚無庫存異動、預留或交易時，以一次性的 `OPENING_BALANCE` 建立期初庫存，以便展示與正式導入時都有可追溯的初始數量。 |
| US-27 | 財務主管 | 身為財務主管，我希望在保留修改前後紀錄的情況下，更正正式應收的外部發票號碼或日期，以便修正輸入錯誤而不改變系統計算的應收金額。 |
| US-28 | 業務主管／採購主管 | 身為對應主檔主管，我希望直接停用或重新啟用已核准的業務主檔並填寫原因，以便控制新交易可用資料，同時保留歷史交易與異動紀錄。 |
| US-29 | 採購主管 | 身為採購主管，我希望依商品需求與分析結果維護以庫存基準單位表示的安全庫存，並保留異動紀錄，以便缺貨風險與一般補庫使用一致的政策數值。 |

## 後續補充欄位

每則 User Story 後續應補充：

- 對應痛點與產品目標。
- 交付優先級。
- 前置條件與相依 Story。
- Given／When／Then 驗收條件。
- 權限與資料範圍。
- 例外及錯誤處理。

跨 Story 的 Given／When／Then 情境、共用測試資料、端到端腳本及整體通過條件集中記錄於 [15-acceptance-test-plan.md](15-acceptance-test-plan.md)，本文件不重複展開。
