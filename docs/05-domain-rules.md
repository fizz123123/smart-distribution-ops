# 領域與資料規則

> 文件版本：v1.0  
> 建立日期：2026-09-29  
> 最後更新：  
> 文件定位：集中定義跨功能共用的名詞、狀態、公式與交易規則；本文件不等同資料庫設計。

## 核心名詞

- **負責業務**：SO 上獨立於建立者的業務歸屬。Web 建單預設為建立者；LINE 建單預設為完成綁定的系統帳號；主管代建時必須指定負責業務。
- **必要交貨資料**：要求交貨日、交貨方式、交貨地點或取貨方式、收貨聯絡資訊及必要備註。要求交貨日與交貨方式必填；客戶自取時可不填交貨地點及收貨聯絡資訊。
- **已辨識客戶與商品**：具有已核准且啟用的客戶、有效公司料號、可使用的客戶料號對應，以及有效交易單位。
- **幣別範圍**：本次專題只接受 TWD。其他幣別不提供建立、修改、匯入、API 或分析功能。
- **SO 送審快照**：SO 送審時保存當下選用的料號對應、價格、稅率、付款條件、單位換算與交貨資料。主檔後續變更不得直接改寫既有快照。

## 主檔啟用與停用

- 客戶、公司料號及客戶料號對應由 SALES_MANAGER 啟用、停用或重新啟用；供應商由 PURCHASING_MANAGER 處理。
- 初次建立仍須完成原有核准或覆核流程。已核准主檔的停用與重新啟用不另走核准，但必須填寫原因並保存操作者、時間及異動前後值。
- 重新啟用前，系統須重新檢查唯一性、必要關聯與資料衝突。已被交易引用的主檔不得實體刪除。
- APP_ADMIN 不得因帳號管理權限而啟用或停用業務主檔。
- 客戶價格不使用一般啟停狀態，依 `ACTIVE / REPLACED / REVOKED` 等價格版本狀態處理；付款條件則由 FINANCE_MANAGER 直接設定。

## 客戶料號與價格

客戶料號對應與客戶價格是兩個不同概念：

- 客戶料號對應用來把客戶使用的料號連到公司內部料號。
- 客戶價格用來保存該對應關係下的未稅 TWD 單價、計價單位及版本狀態。

本次專題只保存單一單價，不處理生效期間、階梯價格、折扣公式、合約量或多幣別。價格狀態為：

```text
PENDING_REVIEW / ACTIVE / REJECTED / REPLACED / REVOKED
```

- 新價格核准後立即成為 `ACTIVE`；同一客戶料號與計價單位最多一筆 `ACTIVE`，原版本在同一交易中轉為 `REPLACED`。
- `REVOKED` 只用於價格本身錯誤；`REPLACED` 與 `REVOKED` 都不可供新 SO 使用。
- 完全缺少 `ACTIVE` 價格時，仍可保存待補資料的 SO 草稿，但不得送審；業務須先完成客戶價格建檔與覆核，SO 不提供任意輸入單價以繞過價格覆核。
- SO 送審時保存價格來源、計價單位、未稅單價及固定 5% 稅率，後續換價不得改寫既有交易。
- 待核准期間若客戶、料號對應或公司料號已停用，SO 不得核准；其他主檔異動則提示主管依快照核准或退回重送。
- 待核准 SO 引用的價格若因新版覆核而轉為 `REPLACED`，不阻擋核准，仍使用送審快照；若因價格錯誤轉為 `REVOKED`，系統拒絕核准，由主管人工退回後再由業務依目前 `ACTIVE` 價格重新送審。
- 系統不得因價格被撤銷而自動將待核准 SO 改為退回；退回必須由具權限者執行並留下意見。已核准 SO 即使原價格日後轉為 `REVOKED`，既有快照、出貨與應收流程仍不回溯修改；必要修正透過餘量取消或另行定義的例外流程處理。

## 安全庫存政策

- 每個公司料號建立時同步建立安全庫存政策，數量以庫存基準單位保存，預設為 0。
- 安全庫存由 PURCHASING_MANAGER 或具相應細部權限者維護；倉管、業務主管及營運主管可依其查看權限讀取，但不得修改。
- 修改安全庫存不另走核准流程，但須保存修改前後值、操作者與時間。儀表板計算的建議安全庫存只供決策參考，不得自動覆寫設定值。

## 商品單位換算

每個商品須設定一個庫存基準單位，並可設定允許的銷售單位、採購單位、常用別名及換算倍率。例如庫存以米為基準，可設定 `1 捲＝20 米`。

SO、PO 與庫存異動須保存：

- 使用者輸入數量與單位。
- 交易當下的換算倍率。
- 換算後的基準數量。

庫存預留、入庫、出庫及可用量全部以基準數量計算。主檔換算倍率修改後，不回頭改寫既有交易。

## 庫存、預留與異動規則

本次專題只將完成驗收且可供出貨的合格數量計入系統庫存。到貨損壞或規格不符數量保留於 PO 驗收紀錄，用於處理補貨或短收結案，不建立隔離、損壞、批號或序號庫存。

預留代表已承諾給特定 SO 明細的數量，不是實體庫存狀態，也不改變可出貨實體數量。

```text
有效預留數量
＝原始預留數量－已出貨使用數量－已釋放數量

可用庫存
＝可出貨實體數量－有效預留數量
```

- PO 驗收的合格數量增加可出貨實體數量；損壞與規格不符數量不計入庫存。
- SO 核准時，系統依當下可用庫存建立預留；不得超額預留，但不改變可出貨實體數量。
- 關聯 PO 合格入庫時，若來源 SO 仍有需求，系統為該 SO 明細建立預留；超出需求的合格數量成為一般可用庫存。
- DO 過帳時，系統扣減可出貨實體數量，並將對應預留標記為已使用。
- SO 未出貨餘量取消核准後，對應預留被釋放，使相同數量恢復可供其他需求使用。
- 收貨過帳前須顯示 PO、品項、合格、損壞、規格不符與入庫結果供倉管確認。過帳後收貨紀錄不得修改；本次專題不提供收貨沖銷。原收貨品項或數量若登錄錯誤，不得以一般庫存調整假裝修正 PO 收貨資料，正式沖銷列為後續擴充。
- 收貨完成後才發現的實體損壞或盤點差異，以倉管主管直接過帳的庫存調整處理，不另走通用核准流程；調整必須保存商品、數量、原因、操作者及時間。
- 期初庫存以 `OPENING_BALANCE` 類型的庫存調整建立，只允許正數，且公司料號尚無庫存異動、預留或交易時才能執行；每個公司料號只能建立一次。
- 庫存調增可直接執行；調減不得超過當下可用庫存。若調減會使可出貨實體數量低於有效預留總量，系統拒絕操作並列出受影響的 SO；侵蝕預留的例外處理不納入本次專題交付。
- 已過帳調整狀態為 `POSTED` 且不直接修改。登錄錯誤時新增相反方向的調整及庫存異動並關聯原調整，原調整標記為 `REVERSED`；新調整仍須符合實體數量非負且不得侵蝕預留的限制。
- 庫存調整不產生預留事件，也不自動或手動改配給既有缺料 SO。
- 所有入庫、出貨與庫存調整均須保存不可任意修改的庫存異動紀錄，使目前實體數量可由異動紀錄重新計算。

## SO 缺料與 PO 供應數量

為避免把 PO 草稿誤認為供應商已接單，系統分開呈現：

- **已規劃未下單量**：來自未取消的關聯 PO 草稿、待核准及退回待修改數量，用來避免同一缺料重複建立 PO，但尚不代表供應商已接單。
- **採購在途量**：只計入已核准或部分收貨，且尚未合格入庫或取消的 PO 數量。
- **尚待規劃供應量**：仍未預留、且尚未被任何未取消關聯 PO 涵蓋的需求。

```text
SO 未預留需求
＝有效訂購基準數量－已出貨基準數量－已預留基準數量

尚待規劃供應量
＝SO 未預留需求－已規劃未下單量－採購在途量

採購在途量
＝已核准採購量－合格入庫量－已取消量
```

只有尚待規劃供應量大於 0 時，才能再由 SO 一鍵建立關聯 PO 草稿。SO 頁面分別顯示已預留、已規劃未下單、採購在途與尚待規劃數量；PO 核准後，相應數量由已規劃未下單轉為採購在途。

關聯 PO 取消，或短收後明確結案時，未補足量重新成為尚待規劃供應量。一般補庫 PO 不綁定 SO，其合格入庫量全部增加可出貨實體數量。

- 已核准且尚未有任何已過帳收貨的 PO，可由 PURCHASING_MANAGER 直接取消並填寫原因；PO 與正式 PDF 標記取消／作廢，未到貨量移出採購在途。
- PO 已部分收貨後不得整張取消。PURCHASING_MANAGER 可直接執行短收結案並填寫原因；已入庫部分維持不變，未到貨餘量轉為取消量，明細轉為 `CLOSED_SHORT`。
- PO 取消或短收結案後，關聯 SO 未被補足的數量重新成為尚待規劃供應量。

一般補庫合格入庫、其他 SO 釋放預留或庫存調增所增加的可用庫存，本次專題不自動也不手動改配給既有缺料 SO。


## DO 與出貨規則

- SO 已核准且本次預計出貨量都有有效預留時，業務才能通知出貨並建立 DO 草稿。
- DO 狀態為 `DRAFT / READY / POSTED / VOIDED`；`READY` 代表揀貨及數量確認完成、正式 DO PDF 已產生，等待交付司機並過帳。
- 同一 SO 明細所有未過帳、未作廢 DO 數量加總不得超過有效預留；建立或修改 DO，以及過帳時都須在鎖定狀態下重新檢查。
- 產生正式 DO PDF 不等於出庫；倉管交付司機並執行過帳才移出庫存。
- 系統分別保存預計出貨日、實際出貨日及操作時間。
- DO 草稿保存預計出貨量；倉管完成揀貨時確認實際出貨量，實際量須大於 0 且不得超過預計量。少出的差額不使用預留，仍保留於來源 SO 明細。
- `DRAFT` 或 `READY` 可作廢；`READY` 作廢時正式 PDF 一併標記作廢，但不扣庫存或使用預留。需更正時建立新 DO，每張 DO 只保存一份正式 PDF，不建立同一 DO 的文件版本鏈。
- 同一 DO 只能成功過帳一次。
- `POSTED` 不直接作廢；後續退貨與反向交易不在本次專題範圍。
- 一張 SO 可對應多張 DO；每張已過帳 DO 各自產生一筆應收。

## 核准與授權規則

- 使用者可透過多個角色取得預設權限，也可被個別授予角色以外的權限；本次專題不提供個別 `DENY`。
- 任何人不得修改自己的角色或個別權限，授權異動須保存操作者、原因、有效期間與異動前後內容。
- 核准者不得是目標資料的建立者，也不得是該輪核准申請的送審者。
- 原核准人若建立或代為送審資料，案件須改由其他具相應權限者或營運主管核准。
- 核准歷程須保存實際操作者、操作角色、是否為替代核准、結果、意見及時間。

## 簡化財務與應收

新客戶付款條件預設為 `DUE_0`。只有財務主管或具相應細部權限者可直接修改客戶付款條件；其他角色只能查看。修改不另走核准流程，但須保存修改前後值、原因、操作者及時間。SO 送審時保存當下的付款條件快照，客戶主檔後續變更不改寫既有 SO。

本次專題付款條件：

```text
DUE_0 到期日＝DO 實際出貨日
NET_30 到期日＝DO 實際出貨日＋30 個日曆日
NET_60 到期日＝DO 實際出貨日＋60 個日曆日
```

`DUE_0` 只表示到期日等於實際出貨日，不進行出貨前收款檢查，也不阻擋 DO 過帳。

應收金額：

```text
未稅小計＝Σ（DO 實際出貨數量×SO 未稅單價快照）
營業稅＝未稅小計×5%
應收含稅總額＝未稅小計＋營業稅
```

本次交付的 TWD 文件總額與稅額在文件層級四捨五入至整數元。DO 過帳、應收草稿、正式應收與儀表板使用同一套後端金額計算結果。

應收狀態包含：

- `PENDING_CONFIRMATION`：DO 過帳後自動建立，待財務確認。
- `OPEN`：財務核對並填入外部發票資料後確認。
- `PARTIALLY_PAID`：已有部分收款，但未收餘額仍大於 0。
- `PAID`：未收餘額為 0。

正式應收確認後，FINANCE_MANAGER 可直接更正外部發票號碼或日期，但不得修改系統計算的應收金額、付款條件、到期日或來源 DO。更正必須填寫原因、重新檢查發票號碼唯一性，並保存修改前後值、操作者與時間；應收狀態維持不變。

```text
0＜本次核銷金額≤未收餘額

未收餘額
＝正式應收含稅金額－已核銷收款金額
```

`OVERDUE` 是動態標記：到期日早於今日且未收餘額大於 0。即將到期採閉區間：`今日≤到期日≤今日＋7 天`，包含第 7 天。

本次專題暫不處理預收、月底彙整請款、多張 DO 合併應收、退貨、折讓、退款、溢收、呆帳、跨客戶沖帳、多幣別、正式會計分錄、供應商請款、應付帳款及供應商付款。PO 上的未稅採購單價只代表已核准的採購承諾，不代表已付款金額、實際現金支出或會計認列成本。
