## D-001　不建立批號與序號管理

- **狀態**：已採用
- **決策日期**：2026-10-04

### 決策

本次專題不建立批號與序號管理。系統透過庫存異動紀錄與單據關聯，支援數量追溯與單據追溯；物料品質問題以「供應商與到貨期間」對照出貨紀錄，進行範圍追溯。

### 理由

商品屬低單價耗材，且小型倉庫難以落實分批擺放與標示，系統批號資料無法保證與現場一致。

### 影響

- 庫存以公司料號、可出貨實體數量、預留及庫存異動紀錄管理，不建立批號、序號、隔離或損壞庫存狀態。
- 入庫與出貨仍須保留來源單據、供應商、實際日期、品項與數量，以支援範圍追溯。
- 若未來業務需要精確追蹤特定批次，須同步調整現場收貨、儲位及標示流程後再擴充。

## D-002　採購單價於 PO 輸入，不建立供應商價格主檔

- **狀態**：已採用
- **決策日期**：2026-10-04

### 決策

本次專題不建立供應商價格主檔。採購單價於建立 PO 時輸入，系統預設帶入同一供應商、同一商品最近一次已核准 PO 的單價；本次 PO 採購單價由採購主管於 PO 核准時把關。

### 理由

- 採購價格可能隨詢價結果及交易時間變動，本次專題保存每張已核准 PO 的採購單價，作為當次採購承諾紀錄。
- 可沿用歷史 PO 降低重複輸入，同時保留採購人員修改本次價格的彈性。
- 避免在尚未確認供應商報價維護流程前，引入額外的價格主檔與有效期間規則。

### 影響

- PO 明細須保存本次採購單價及幣別；本次專題幣別限定為 TWD。
- 系統帶入的歷史單價只是預設值，不代表供應商的有效報價。
- 採購主管核准時須能比較本次單價與最近一次已核准 PO 單價。
- 若找不到相同供應商及商品的歷史 PO，採購人員須自行輸入單價。

## D-003　PO 可整合多張 SO，但每筆 PO 明細只對應一筆 SO 明細

- **狀態**：已採用
- **決策日期**：2026-10-04

### 決策

一張 PO 可以包含同一供應商之多張 SO 的採購需求，也可以同時包含一般補庫需求；每一筆 PO 明細只能對應一筆 SO 明細，或標示為不關聯 SO 的一般補庫。

### 理由

- 允許採購將同一供應商的需求合併為一張對外 PO。
- 每筆 PO 明細仍保有單一且明確的需求來源，本次專題不加入採購明細分配表。
- 關聯 PO 的到貨、短收與取消可直接回溯來源 SO 明細。

### 影響

- PO 表頭只能對應一個供應商及 TWD 幣別。
- 關聯採購明細必須保存來源 SO 明細；一般補庫明細不得保存來源 SO 明細。
- 同一商品若供應不同 SO 明細，須拆成不同 PO 明細，不合併為一筆。
- 同一 SO 明細可由多張 PO 或多筆 PO 明細補足，但所有未完成關聯採購量不得造成重複規劃。
- 已知超出來源 SO 尚待規劃供應量的採購數量，應另列為一般補庫明細；若 PO 下單後因 SO 減量或取消而產生多餘到貨，合格數量轉為一般可用庫存。

## D-004　正式保存的 PDF 限於 PO 與 DO

- **狀態**：已採用
- **決策日期**：2026-10-04

### 決策

本次專題永久保存的正式 PDF 僅包含採購單 PO 與出貨單 DO。每張 PO 或 DO 只保存一份正式 PDF；再次列印直接讀取原檔，不在同一單據下建立 PDF 版本鏈。實際檔案不直接存入一般資料表。

### 理由

- PO 是提供供應商的正式下單文件，DO 是隨貨交付並證明出貨內容的正式文件。
- 揀貨單屬內部作業文件，可依目前 DO 資料即時產生，不需永久保存版本。
- SO、應收、儀表板及 AI 摘要可在系統中查閱；統一發票由外部發票系統處理。

### 影響

- 文件資料模型在本次專題只需支援 `PURCHASE_ORDER` 與 `DELIVERY_ORDER` 類型。
- 正式文件內容有誤時，取消或作廢原單據及 PDF，再建立新單據；已作廢檔案仍保留，不覆蓋原始檔案。
- 揀貨單、查詢報表或其他匯出檔案若未來需要保存，再擴充文件類型與保存規則。

## D-005　收款與應收採表頭及核銷明細模型

- **狀態**：已採用
- **決策日期**：2026-10-04

### 決策

收款採用 `payment` 表頭與 `payment_allocation` 核銷明細。一筆收款可核銷同一客戶的多筆正式應收，一筆應收也可由多筆收款逐步核銷。

### 理由

- 一筆實際匯款可能同時支付多張發票或多筆應收，系統收款紀錄應與實際入帳一致。
- 核銷明細可明確回答一筆款項分配至哪些應收，以及各自核銷多少。
- 單筆收款只核銷一筆應收時，仍可使用相同模型，不需要另一套流程。

### 規則

- 同一筆收款的所有核銷應收必須屬於同一客戶，且狀態為可核銷的正式應收。
- 每筆核銷金額須大於零，且不得超過該應收當下的未收餘額。
- 本次專題不處理預收、溢收或未分配款；所有有效核銷明細加總必須等於收款金額。
- 系統可依到期日、實際出貨日及應收編號提供預設分配順序，但須由財務確認後才成立。
- 確認收款時須在同一資料庫交易中鎖定相關應收、重新驗證未收餘額並建立核銷明細，避免重複核銷。
- 已確認收款不直接修改。登錄錯誤時由財務主管作廢整筆收款，保留原核銷明細、作廢原因、操作者與時間，再重新登錄。
- 計算未收餘額時，只加總狀態為 `CONFIRMED` 的收款核銷；收款作廢後，相關核銷失效並重新計算應收狀態。

### 影響

- `payment` 保存客戶、收款日期、收款金額、方式、外部參考號碼及確認或作廢狀態。
- `payment_allocation` 保存收款、應收及核銷金額。
- 應收的 `OPEN`、`PARTIALLY_PAID` 與 `PAID` 狀態依有效核銷金額判斷。
- `PENDING_CONFIRMATION` 應收不得建立核銷明細。

## D-006　驗收異常不建立庫存狀態

- **狀態**：已採用
- **決策日期**：2026-10-04

### 決策

本次專題不建立隔離或損壞庫存狀態。PO 到貨驗收分別記錄合格、損壞及規格不符數量，只有合格數量增加可出貨實體庫存；異常數量保留於驗收紀錄，由採購與供應商確認補貨或短收結案。

### 理由

- 目前商品為低單價工程耗材，沒有明確的延後檢驗、隔離後放行或損壞品庫存管理需求。
- 建立隔離與損壞狀態會連帶增加移轉、解除、退貨及報廢流程，但對目前核心營運分析的貢獻有限。
- 保留驗收異常數量已足以解釋短收、追蹤供應商到貨品質及處理補貨。

### 影響

- 損壞與規格不符數量不計入系統庫存，也不可用於 SO 預留或 DO 出貨。
- 收貨後才發現的損壞，以有原因、操作者及時間的庫存調減處理，不另建立損壞庫存桶。
- 庫存調減若會使可出貨實體數量低於有效預留總量，系統拒絕操作；侵蝕預留的庫存例外不納入本次專題交付。
- 若未來需要管理待退供應商或隔離後放行，再擴充驗收異常的後續庫存流程。

## D-007　庫存與預留採目前狀態加不可修改異動明細

- **狀態**：已採用
- **決策日期**：2026-10-04

### 決策

實體庫存與預留使用一致的雙層模型：`inventory_balance` 與 `inventory_reservation` 保存目前狀態，`inventory_transaction` 與 `inventory_reservation_event` 保存只新增、不修改、不刪除的異動歷程。

### 理由

- `inventory_balance` 為每個公司料號提供可鎖定的目前餘額列，使同時核准多張 SO 時能依序檢查並建立預留，避免超額承諾。
- 目前餘額可直接查詢，並能由不可修改的異動明細重新驗算。
- 一筆 SO 明細可能因原有庫存、分批入庫、分批出貨與部分取消而多次增減預留，事件明細可保留每次來源。
- 庫存與預留採相同模式，能降低團隊理解與實作兩套規則的成本。

### 規則

- 每個公司料號建立時即建立一筆 `inventory_balance`，即使目前數量為零；料號停用後仍保留餘額及歷程。
- `inventory_balance.on_hand_qty` 等於該公司料號所有有效實體庫存異動的加總。
- 每筆 SO 明細最多對應一筆 `inventory_reservation`；其 `open_qty` 等於 `RESERVE` 事件加總減去 `CONSUME` 與 `RELEASE` 事件加總，且不得小於零。
- 可用庫存等於 `on_hand_qty` 減去該公司料號所有 `open_qty` 加總。
- `on_hand_qty` 不得低於有效預留總量。庫存調減若會侵蝕既有預留，系統拒絕操作。
- SO 核准、關聯 PO 合格入庫及庫存調減等操作須先鎖定對應餘額列，再重新驗證數量並於同一資料庫交易中更新目前狀態與新增事件。
- 多商品交易依公司料號固定順序鎖定餘額列，降低死鎖風險。
- 期初數量以 `OPENING_BALANCE` 異動建立；已完成異動若需更正，新增反向異動，不修改或刪除原紀錄。

### 影響

- 實體庫存至少包含 `inventory_balance` 與 `inventory_transaction`。
- 預留至少包含 `inventory_reservation` 與 `inventory_reservation_event`。
- `RESERVE` 來源包含 SO 核准與關聯 PO 合格入庫；`CONSUME` 來源為 DO 過帳；`RELEASE` 來源為 SO 未出貨餘量取消。
- 所有數量以公司料號的庫存基準單位保存。
- 自動化測試與展示前須能執行一致性檢查，驗證餘額、異動、預留與事件加總一致。

## D-008　個別權限只提供額外授權

- **狀態**：已採用
- **決策日期**：2026-10-05

### 決策

使用者可透過角色取得預設權限，也可被個別授予角色以外的權限；本次專題不提供個別 `DENY`。任何人都不得修改自己的角色或個別權限，所有授權異動均保留操作者、原因、有效期間與異動前後內容。

### 理由

- 現階段需求是支援兼任與額外授權，尚無「保留角色但排除其中一項權限」的明確情境。
- 移除 `DENY` 可避免角色允許、個別允許及個別拒絕之間的優先順序造成前後端判斷不一致。

### 影響

- 個別權限資料使用 `user_permission_grant`，不保存 `GRANT/DENY` 效果欄位。
- 若使用者不應取得某項角色權限，應調整角色指派或角色本身的權限組合。

## D-009　客戶價格核准即生效並保留版本

- **狀態**：已採用
- **決策日期**：2026-10-05

### 決策

客戶價格不設定生效日與失效日。新價格經業務主管覆核後立即成為 `ACTIVE`；同一客戶料號與計價單位最多一筆 `ACTIVE`，原價格同時轉為 `REPLACED`。價格本身錯誤時改為 `REVOKED`，不再供新交易使用。

SO 草稿可以暫時缺少價格，但送審時必須引用一筆 `ACTIVE` 客戶價格；SO 不提供任意輸入成交單價以繞過價格覆核。送審時保存價格來源、計價單位及未稅單價快照，後續換價不改寫既有交易。

### 規則

- 價格狀態至少包含 `PENDING_REVIEW / ACTIVE / REJECTED / REPLACED / REVOKED`。
- 新價格啟用及舊價格轉為 `REPLACED` 須在同一資料庫交易完成。
- `REPLACED` 與 `REVOKED` 僅供歷史查詢，不可供新 SO 送審。

## D-010　庫存調整只處理未被預留的數量

- **狀態**：已採用
- **決策日期**：2026-10-05

### 決策

庫存調整不另走通用核准流程，只允許倉管主管或具相應細部權限者直接過帳，且必須填寫原因。調增可直接執行；調減不得超過當下可用庫存。若調減會使 `on_hand_qty` 低於有效預留總量，系統拒絕操作並列出受影響的 SO，侵蝕既有預留的處理不納入本次專題交付。

調整完成後狀態為 `POSTED` 且不直接修改。登錄錯誤時新增相反方向的調整及庫存異動，並關聯原始調整；原始調整標記為 `REVERSED`，相反方向調整仍須通過相同的非負數與預留一致性檢查。庫存調整不產生預留事件，也不重新分配既有缺料 SO。

## D-011　建立者與本輪送審者均不得核准

- **狀態**：已採用
- **決策日期**：2026-10-05

### 決策

核准者不得是目標資料的建立者，也不得是該輪核准申請的送審者。若原核准人建立或代為送審資料，必須由其他具相應核准權限者或營運主管處理。

### 影響

- 後端核准服務須同時比對目標建立者及本輪送審者。
- 核准歷程保存實際操作角色及是否為替代核准。
- 整合測試須涵蓋建立者自行核准、代送審者自行核准、一般核准及替代核准情境。

## D-012　DO 草稿占用與正式文件狀態

- **狀態**：已採用
- **決策日期**：2026-10-05

### 決策

DO 使用 `DRAFT / READY / POSTED / VOIDED` 狀態。`READY` 表示揀貨及數量確認完成、正式 DO PDF 已產生，等待貨物與文件交付司機並執行出貨過帳。

### 規則

- 同一 SO 明細所有未過帳、未作廢 DO 數量加總不得超過有效預留。
- 建立或修改 DO，以及 DO 過帳時都必須在鎖定狀態下重新檢查數量。
- `DRAFT` 或 `READY` 可作廢；`READY` 作廢時正式 PDF 一併標記作廢，但不扣庫存或使用預留。需更正時建立新 DO，不在同一 DO 下建立 PDF 版本。
- `POSTED` 不直接作廢；後續退貨與反向交易不在本次專題範圍。

## D-013　核准與正式文件使用可驗證目標關係

- **狀態**：已採用
- **決策日期**：2026-10-05

### 決策

核准申請及正式文件與核心業務資料之間使用可由資料庫驗證的明確外鍵，不以任意文字類型搭配任意 ID 作為正式業務關係。每筆資料恰好只能指向一種目標，且目標須與業務類型一致。

`audit_log` 只作為操作紀錄，不是業務正確性的依據，因此可以保留目標類型與目標 ID 的通用記法。

## D-014　付款條件由財務主管直接設定

- **狀態**：已採用
- **決策日期**：2026-10-05

### 決策

新客戶預設 `DUE_0`。只有財務主管或具相應細部權限者可以直接將客戶付款條件設定為 `DUE_0 / NET_30 / NET_60`，不建立付款條件申請表或核准流程。其他角色只能查看。

### 影響

- 每次修改須保存修改前後值、原因、操作者及時間。
- SO 送審時使用當下客戶付款條件並保存快照；已送審 SO 不因客戶主檔變更而改寫。

## D-015　偏好供應商直接保存於公司料號

- **狀態**：已採用
- **決策日期**：2026-10-05

### 決策

本次專題不建立 `supplier_item`。公司料號可保存一個可為空的偏好供應商，建立 PO 草稿時作為預設值；採購仍可改選其他已啟用供應商。

### 影響

- 系統不提供候選供應商清單或供應商商品型錄。
- 實際歷史供應關係與採購價格由 PO 查詢。

## D-016　LINE AI 先採單輪解析與確認

- **狀態**：已採用
- **決策日期**：2026-10-05

### 決策

## D-026　出貨採計畫數量與實際數量分離

- PO 草稿或待核准數量屬已規劃未下單，只有已核准 PO 的未到貨量列為採購在途。

## D-029　正式 PDF 以短效 S3 Presigned URL 下載

- **狀態**：已採用

### 決策

## D-030　前端與 API 分離入口，後端改採 ALB HTTPS

- **狀態**：已採用
- **決策日期**：2026-10-05

### 決策

Vue 3 前端維持部署至私有 S3，由 CloudFront 提供 HTTPS 與靜態內容。Spring Boot API 使用獨立的 `api` 網域，部署至 Elastic Beanstalk Load-balanced Environment，由 Application Load Balancer 搭配 ACM 憑證提供 HTTPS。展示環境的 Beanstalk 最小與最大執行個體數均設為 1，保留單一應用執行個體，但由 ALB 終止對外 TLS。

CloudFront 不再將 `/api/*` 代理至後端。Vue 直接呼叫 `https://api.<domain>/api/v1`，後端 CORS 只允許指定的前端 CloudFront 或自訂網域與本機開發來源。LINE webhook 也直接使用 API HTTPS 網域。

### 影響

- Internet 到 API 的連線由 ALB 使用 ACM 憑證加密，不依賴 Single Instance 上手動維護 Nginx 憑證。
- ALB 到 Beanstalk EC2 的應用連線先採 VPC 內 HTTP，EC2 Security Group 只允許 ALB Security Group 進入。若未來有強制端到端 TLS 要求，再配置執行個體 HTTPS。
- 正式環境需要可控制的 API 網域、DNS 記錄及 ACM 憑證。
- 正式環境也需套用 CORS 允許清單；前端與 API 的域名不同，不再是 CloudFront 同源路由。
- ALB 會增加固定成本，但能簡化對外 HTTPS、健康檢查與後續擴充。
- RDS MySQL、私有文件 S3、OpenAI API、模組化單體及 Presigned URL 等既有決策不變。

## D-032　營收、變化分析與 AI 營運摘要採固定可追溯口徑

- **狀態**：已採用
- **決策日期**：2026-10-05

### 決策

本專題將營收定義為統計期間內已過帳 DO 的實際出貨未稅金額，並以 DO 過帳日歸屬期間。儀表板預設比較目前自然月與前一自然月；使用自訂日期時，前期為緊接本期之前的等長期間。

營收變化由後端依客戶及商品計算本期與前期差額，分別列出增加與減少最多的前三名。不同商品具有不同單位，不計算全公司平均出貨單價；數量與價格只在同一公司料號及一致基準單位下比較。未出貨訂單與供應狀態只能作為可能原因或相關變化，沒有直接證據時不得宣稱因果關係。

交易降溫以已核准 SO 日期計算。至少有 3 張已核准 SO 才建立歷史平均交易週期；距上次交易天數超過平均週期 1.5 倍為中風險，超過 2 倍為高風險，資料不足時不評級。

AI 營運摘要由營運主管在 Web 儀表板按需產生，沿用當下期間與篩選。每次產生均保存結構化輸入、固定 Structured Output、來源、模型、狀態與時間；本次不提供排程、Email 或 PDF。AI 失敗不得影響儀表板，且 AI 引用的來源識別碼須由後端驗證。

### 影響

- 淨接單、營收、未出貨與應收分別代表接單、履約、待履約及收款階段，不混用日期與金額口徑。
- 前期營收為 0 時不計算變化率，只呈現絕對變化與資料限制。
- AI 只負責整理後端已計算的指標，不自行計算營收、排名、風險或資料關聯。
- AI 不取代個人作業待辦；待核准與待處理由 HOME-01「我的工作台」承接，儀表板只提供營運風險清單及工作台入口，不另建立待辦中心。
- 本專題的營收是營運分析口徑，不宣稱已完成會計總帳或法定收入認列。

## D-033　SO 核准依價格撤銷狀態判斷，不受正常換價影響

- **狀態**：已採用
- **決策日期**：2026-10-06

### 決策

SO 送審後，引用價格因新版覆核而轉為 `REPLACED` 時，不阻擋核准，系統仍使用送審時保存的價格快照。引用價格因資料錯誤而轉為 `REVOKED` 時，系統拒絕核准並回傳 `SO_PRICE_REVOKED`，但不自動改變 SO 狀態；主管須手動退回並留下意見，業務重新送審時再引用目前的 `ACTIVE` 價格。

核准時也須重新確認客戶、客戶料號對應及公司料號仍為啟用狀態。上述主檔停用時同樣阻擋核准。

### 影響

- 價格正常換版不會破壞送審快照的穩定性。
- 錯誤價格撤銷可在交易生效前阻擋核准，且退回責任與意見可追溯。
- 已核准 SO 不因來源價格日後被撤銷而回溯修改，也不因此阻擋既有出貨與應收；必要修正透過餘量取消或另行定義的例外流程處理。

## D-034　安全庫存由採購主管維護
