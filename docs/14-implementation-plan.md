# 實作規劃

> 文件版本：v1.0  
> 建立日期：2026-10-06  
> 最後更新：  
> 文件定位：將既有產品需求、領域規則、資料模型、狀態操作及 API 契約拆成可依序驗證的開發階段，供前後端協作、進度追蹤與風險控制使用。

---

## 1. 規劃目標

本文件回答以下問題：

1. 功能應依什麼順序實作？
2. 每個階段前後端要交付什麼？
3. 哪些條件完成後才能進入下一階段？
4. 哪些技術問題需要提早驗證？
5. 如何確保核心交易資料最後能供儀表板與 AI 使用？

本文件不新增產品功能。產品範圍、業務規則與資料責任仍以現有需求及設計文件為依據；實作中若需要改變範圍或規則，須同步更新相關文件及 [決策紀錄](09-decision-log.md)。

## 2. 實作原則

- 採垂直切片：每個階段同時完成必要資料結構、後端規則、API、前端畫面及測試，不先建立大量無法操作的空殼模組。
- 先完成可信的交易資料流，再實作依賴交易資料的儀表板與 AI。
- 前端不得自行推測權限、狀態或計算結果；成功操作後使用後端回傳的最新資料更新畫面。
- 跨模組核心資料異動由 Spring Boot 同步服務協調，並在同一筆 MySQL 交易中完成。
- 每個階段均包含正常流程、權限拒絕、狀態錯誤及併發或重複操作的基本測試。
- AI 與外部服務失敗不得破壞既有交易資料，也不得阻擋儀表板的規則型分析。
- 開發順序只代表依賴與風險安排，不代表後段功能可以不交付；若要調整交付範圍，須另行記錄決策。

## 3. 三個月實作階段

下列週次是約略安排，可依團隊速度平移；階段完成條件比日期更重要。

| 階段 | 建議週次 | 可驗證成果 |
| --- | --- | --- |
| P0 專案基礎與技術驗證 | 第 1 週 | 前後端可啟動、可連接 MySQL、測試及展示環境風險已驗證 |
| P1 登入、權限與共用核准 | 第 1～2 週 | 使用者可登入；API 權限、自我授權及核准分離規則可驗證 |
| P2 主檔與交易條件 | 第 2～3 週 | 客戶、供應商、料號、客戶料號、價格及付款條件可供交易查用 |
| P3 SO 與庫存預留 | 第 3～5 週 | SO 可建立、送審、核准並正確預留庫存及顯示供應狀態 |
| P4 PO、驗收入庫與補足預留 | 第 5～7 週 | 缺料可轉 PO，合格入庫後補足來源 SO 需求 |
| P5 DO、PDF、應收與收款 | 第 7～9 週 | 可完成出貨過帳、扣庫存、產生應收並完成部分或全額核銷 |
| P6 儀表板與下鑽 | 第 9～10 週 | 四組分析、六張指標卡、趨勢及待處理清單可由交易資料重現 |
| P7 AI 營運摘要 | 第 10～11 週 | AI 依限定結構化資料產生附來源摘要，失敗不影響儀表板 |
| P8 LINE AI 建立 SO 草稿 | 第 10～11 週 | 完成本人綁定、單輪解析、預覽確認及建立 SO 草稿 |
| P9 整合、部署與驗收 | 第 12 週 | AWS 環境可操作，核心情境、權限、資料一致性及展示腳本通過 |

P7 與 P8 可在核心服務穩定後平行進行，但不得各自建立繞過既有服務的交易邏輯。

## 4. 各階段工作內容

### P0　專案基礎與技術驗證

**共同工作**

- 建立 Spring Boot 與 Vue 3 專案結構、環境設定及啟動說明。
- 建立本機 MySQL 開發環境與測試資料庫。
- 統一 API base path、錯誤格式、時間、金額、數量與識別碼格式。
- 建立基本健康檢查及前後端連線測試。
- 決定資料庫結構變更的管理方式，再開始共享資料表實作。

**提早驗證，不代表完成正式功能**

- OpenAI Structured Output 能否依限定 Schema 回傳。
- LINE webhook 簽章驗證及事件防重的最小測試。
- S3 私有物件與 Presigned URL 的最小測試。
- Spring Boot JAR 部署至 Elastic Beanstalk 並經 ALB HTTPS 存取的最小測試。

**完成條件**

- 新成員依 README 可在本機啟動前端、後端及 MySQL。
- 開發、測試及展示環境的機密資訊不進入 Git。
- 四項外部整合至少完成技術可行性驗證，或留下明確阻礙與處理方案。

### P1　登入、權限與共用核准

**後端**

- 使用者、角色、角色權限及個別額外授權。
- JWT 登入、Spring Security 授權及資料範圍基礎。
- 禁止使用者修改自己的授權。
- 共用核准申請與核准動作；檢查核准者不是建立者或本輪送審者。
- 重要授權及核准操作稽核紀錄。

**前端**

- 登入、目前使用者資訊及依權限顯示導覽。
- 我的工作台與待核准入口的最小版本。
- 使用者、角色及個別額外授權管理畫面。

**完成條件**

- 至少準備承辦者、部門主管、營運主管及系統管理員測試帳號。
- 可以重現成功核准、自我核准被拒絕、無權限存取及禁止自我授權。

### P2　主檔與交易條件

**後端**

- 客戶、供應商、公司料號、庫存政策、單位換算。
- 客戶料號與公司料號對應。
- 客戶價格覆核、版本歷史及 `ACTIVE` 價格查用。
- 客戶付款條件由財務主管直接修改並保存異動紀錄。
- 主檔送審、核准、啟用、停用及重新啟用規則。

**前端**

- 主檔清單、詳情、建立、修改、送審及核准畫面。
- 價格、單位與主檔狀態警示。

**完成條件**

- 未啟用主檔及未覆核價格不能用於正式交易送審。
- 交易可查用客戶料號對應、固定單位換算及價格，但不能直接改寫主檔。

### P3　SO 與庫存預留

**後端**

- 期初庫存及不侵蝕預留的庫存調整。
- Web 建立及修改 SO 草稿、送審時保存交易條件。
- SO 核准時鎖定庫存餘額，依可用量建立預留與事件紀錄。
- 顯示已預留、已規劃未下單、採購在途及尚待規劃數量。
- 未出貨餘量取消申請及預留釋放。
- 庫存餘額、異動與預留的一致性檢查。

**前端**

- SO 清單、詳情、建單、送審、核准及供應狀態。
- 庫存查詢、期初庫存及允許範圍內的調整。

**完成條件**

- 兩張 SO 同時核准時不會超額預留。
- 可以從 SO 下鑽至預留及庫存異動來源。
- SO 核准前不能建立關聯 PO 或 DO。

### P4　PO、驗收入庫與補足預留

**後端**

- 從 SO 尚待規劃量建立關聯 PO 草稿，以及一般補庫 PO。
- 同一 PO 可包含多張 SO 需求，但每筆明細最多對應一筆 SO 明細。
- PO 送審、核准、正式 PDF、取消及短收結案。
- 分批驗收；合格數量入庫，異常數量只保留驗收紀錄。
- 關聯 PO 合格入庫後，補足來源 SO 尚未滿足的預留。
- PO 草稿、待核准及已核准數量分別計入正確供應階段。

**前端**

- SO 缺料轉 PO、PO 編輯與核准。
- 收貨驗收、過帳前確認及入庫結果。

**完成條件**

- PO 草稿不列為採購在途。
- 關聯入庫及一般補庫入庫可得到不同且正確的預留結果。
- PO 取消或短收結案後，SO 尚待規劃量能重新計算。

### P5　DO、PDF、應收與收款

**後端**

- 業務通知出貨並以已預留數量建立 DO 草稿。
- 倉管確認實際量、產生正式 DO PDF、交車及出貨過帳。
- 過帳時扣減實體庫存、使用預留並建立唯一應收草稿。
- 財務確認外部發票資料及正式應收。
- 一筆收款分配至同一客戶的一筆或多筆應收。
- 部分收款、全額結清及財務主管作廢錯誤收款。

**前端**

- DO 清單、揀貨、實際出貨量、PDF 及過帳操作。
- 應收確認、未收查詢、收款分配與作廢操作。

**完成條件**

- 同一 DO 只能過帳一次，且只產生一筆應收。
- 收款分配總額等於收款金額，不允許跨客戶、溢收或未分配款。
- 核銷及作廢後的應收狀態與未收餘額均可由明細重算。

### P6　儀表板與下鑽

**後端**

- 六張核心指標卡、近六個月淨接單與營收趨勢。
- 缺貨與履約、交易降溫、即將到期與逾期應收三張清單。
- 接單與營收、缺貨與採購、客戶交易降溫、應收與逾期四組詳情。
- 來源識別碼、資料期間、分析基準日及資料不足標記。

**前端**

- 儀表板首頁、期間與基準日呈現、詳情及來源下鑽。
- 「我的待辦」只連到 HOME-01，不另建立待辦中心。

**完成條件**

- 相同期間與條件下，首頁、詳情與來源明細可以互相驗算。
- 本期指標與截至基準日指標不混用。
- 前期為零或資料不足時，不顯示誤導性的百分比或風險結論。

### P7　AI 營運摘要

**後端**

- 沿用儀表板服務取得限定結構化輸入。
- 使用固定 Structured Output Schema。
- 驗證 AI 回傳的來源識別碼及目前使用者查看權限。
- 保存每次輸入、輸出、模型、狀態、產生者及時間。
- AI 失敗時保留失敗結果，但不影響儀表板。

**前端**

- 由具權限的營運主管按需產生及查看摘要。
- 呈現重要變化、可能原因、建議處理順序、資料限制及來源連結。

**完成條件**

- AI 不直接查詢資料庫、不自行計算指標、不修改交易。
- 摘要數字與相同篩選條件的儀表板一致。
- 每項重要結論至少能連回已驗證的分析明細或交易來源。

### P8　LINE AI 建立 SO 草稿

**後端**

- Web 產生一次性綁定碼、LINE 本人綁定、解除與管理。
- Webhook 簽章驗證、LINE event ID 防重及權限檢查。
- 單輪自然語言解析、後端主檔比對、缺漏及歧義處理。
- 原發起者確認後，呼叫與 Web 相同的 SO 服務建立草稿。

**LINE／Web 呈現**

- 顯示解析結果、比對結果、缺漏、價格警示及確認選項。
- 可由 Web 查看 LINE 建立的 SO 草稿並完成後續送審。

**完成條件**

- 未綁定、停用或無權限使用者不會呼叫 AI 或取得內部資料。
- 缺漏、歧義、逾時或未確認時不建立 SO 草稿。
- AI 不決定公司料號、價格、庫存或權限，也不能送審或核准。

### P9　整合、部署與驗收

- 執行核心流程、權限矩陣、狀態轉換及資料一致性測試。
- 建立匿名化或合理模擬的展示資料，涵蓋正常、分批及例外情境。
- 部署 Vue 3 至私有 S3＋CloudFront；部署 Spring Boot 至 Elastic Beanstalk＋ALB。
- 建立 RDS MySQL、私有文件 S3、Secrets Manager 及 CloudWatch 設定。
- 驗證正式 PDF 的權限與短效 Presigned URL。
- 完成展示腳本、問題清單、備援資料及失敗情境說明。

## 5. 前後端協作方式

每個垂直切片開始前，雙方先確認：

1. 畫面操作及狀態。
2. API request、response 與錯誤格式。
3. 權限代碼與資料範圍。
4. 成功後的狀態及資料異動。
5. 驗收案例及測試帳號。

前端可依 [API 與畫面契約](12-api-and-screen-contracts.md) 使用固定 JSON 範例先行製作；後端完成 API 後，應以相同案例進行串接。API 行為若因實作調整，須同時更新契約及受影響的流程、狀態或資料規則文件。

## 6. 測試與驗收銜接

每個實作階段須依本文件的「完成條件」進行開發內部檢查；詳細案例、共用測試資料、驗收證據與整體通過標準集中維護於 [15-acceptance-test-plan.md](15-acceptance-test-plan.md)，不在本文件重複列出。

測試資料應隨垂直切片逐步建立，並沿用 15 號文件定義的固定代碼及主端到端情境。儀表板與 AI 所需的歷史資料也應由可重現的測試資料建立機制產生，不直接在畫面或 API 回應中硬編結果。

## 7. 實作前待決策事項

以下事項屬技術實作選擇，尚未因本文件而定案：

1. MySQL 結構變更的版本管理方式：Flyway、Liquibase，或團隊維護的版本化 SQL 流程。
2. Spring Boot 及 Vue 3 的測試套件與最低測試門檻。
3. PO／DO PDF 產生函式庫與版型實作方式。
4. OpenAI 模型、逾時、重試及單次成本上限。
5. CI/CD 的執行平台與部署觸發方式。

這些技術選擇確定後，再加入 [決策紀錄](09-decision-log.md)；在此之前不得將其中任一方案描述為既定架構。

## 8. 主要里程碑

| 里程碑 | 驗收結果 |
| --- | --- |
| M1 基礎權限可用 | 可登入、授權、送審、核准與查看稽核紀錄 |
| M2 接單與預留可用 | 主檔可查用，SO 核准後正確預留並顯示缺料 |
| M3 採購與履約可用 | 缺料可採購入庫，DO 可過帳並扣減庫存 |

| M6 LINE 與部署完成 | LINE AI 可建立草稿，AWS 環境可執行完整展示情境 |
