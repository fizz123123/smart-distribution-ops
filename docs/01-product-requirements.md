## 1. 專案定位

整合中小型工程材料經銷商的客戶、商品、訂單、採購、庫存、出貨與應收資料，讓各部門使用同一套一致且可追溯的資料。系統再將資料整理成銷售變化、缺貨風險與客戶交易降溫等營運指標，透過儀表板與 AI 摘要協助管理者發現異常、了解可能原因並排定處理順序。業務也可透過 LINE AI 將客戶需求轉成銷售訂單草稿，減少輸入工作；交易核准與執行仍由授權人員負責。

## 2. 案例業者與需求來源

本專題以中小型保溫與防蝕工程材料經銷商為情境。公司向材料製造商與區域代理商進貨，主要銷售給空調冷凍工程行、機電承包商、工業設備維護商與材料零售通路，也接受少量個人客戶透過臨櫃、電話或 LINE 下單。

受訪對象是一家約 5 人、以工程服務為主並兼售材料的小型業者。專題沿用訪談取得的商品與部分交易作法，但將系統使用情境設定為約 10 人的中小型經銷商，以驗證多角色作業、核准流程與跨部門資料整合。專題角色與流程不完全等同受訪業者的現況。

主要商品包括 PE 保溫管、PE 保溫板、PE 保溫帶、PVC 防蝕膠帶及防落隆 PU 管墊。現行作業主要依靠 Excel、紙本、手寫單據、電話與 LINE。

## 3. 核心痛點

| 問題 | 營運影響 | 本次專題改善方向 |
| --- | --- | --- |
| 客戶料號、公司料號與約定價格分散 | 建單需反覆查證，容易選錯規格或價格 | 保存已覆核的料號對應與價格，建單時由系統查用 |
| 商品名稱、規格、單位不一致 | 易選錯品項或算錯數量 | 統一商品主檔、客戶料號對應與單位換算 |
| 部分客戶透過 LINE 傳送訂購需求，業務外出或無法使用電腦時，無法即時建單 | 只能事後重新整理訊息，訊息也可能被後續對話淹沒，造成延遲處理或漏單 | 具權限的業務可將客戶訊息轉貼或輸入 LINE AI，確認解析結果後，第一時間建立 SO 草稿，之後再回到 Web 補齊資料並送審 |
| 訂單、庫存、採購與出貨各自記錄，跨部門資訊不同步 | 業務無法即時確認可交貨數量，可能超賣、漏採購或延遲出貨 | 串連庫存預留、缺料採購、到貨入庫與出貨過帳，讓各部門隨時掌握可交貨數量與訂單履約進度 |
| 銷售變化缺乏一致指標與原因拆解 | 主管知道業績變動，卻難以判斷原因出在訂單數、平均訂單金額、主要客戶、商品需求，還是出貨遞延 | 分別計算接單與已過帳銷售，比較前後期，並依客戶及商品拆解變化來源 |
| 缺料通常到接單或備貨時才發現 | 可能緊急採購、延誤交貨或流失訂單 | 整合訂單需求、可用庫存、採購在途與預計到貨日，提前標示缺貨風險 |
| 重要客戶交易降溫不易及早察覺 | 常等到客戶長期未下單才發現，錯過確認需求、價格或交期問題的時機 | 比較客戶近期與過往的交易行為，標示交易降溫風險，並附上來源紀錄 |
| 管理資訊與應收資料仰賴人工彙整 | 報表耗時、催收容易遺漏，異常的處理順序也不明確 | 依固定規則計算指標，在儀表板呈現即將到期與逾期應收，再由 AI 營運摘要整理異常與建議處理順序 |

## 4. 專題交付目標

1. 建立客戶、商品、SO、PO、庫存、DO 與應收之間可信且可追溯的資料流。
2. 以角色與權限限制操作，保留建立、覆核、核准、入出庫、過帳與授權異動紀錄。
3. 讓管理者透過一致指標查看銷售變化、缺貨風險、客戶交易降溫及應收狀況。
4. 由 AI 使用後端已整理的結構化資料產生具來源依據的營運摘要。
5. 讓具權限的業務透過 LINE 輸入需求，經釐清、預覽與本人確認後建立 SO 草稿。

## 5. 核心交付功能

| 功能群 | 本次專題交付範圍 |
| --- | --- |
| 主檔資料 | 客戶與供應商建檔及核准；公司料號、客戶料號、料號對應及未稅 TWD 客戶價格覆核；商品單位換算；價格可設定生效日與失效日 |
| 銷售訂單 | Web 與 LINE 建立 SO 草稿；送審時驗證主檔，並保存成交單價、單位換算與付款條件，後續調價不影響既有訂單；主管核准後才預留庫存並開放後續作業 |
| 採購與入庫 | 從 SO 缺料建立關聯 PO 草稿，或建立一般補庫 PO；主管核准後產生 PO PDF；依 PO 驗收入庫並記錄合格與異常數量 |
| 出貨與庫存 | 業務確認本次出貨內容並通知出貨，系統產生 DO；倉管依 DO 揀貨、包裝並產生出貨單 PDF，交付司機後過帳並扣減庫存 |
| 應收 | 每張已過帳 DO 自動產生一筆應收草稿，依現結、30 天或 60 天計算到期日；財務填入外部發票號碼後確認，並登錄部分或全額收款 |
| 帳號與權限 | 支援多角色及個別權限 |
| 營運儀表板 | 呈現接單與已過帳銷售、銷售變化拆解、缺貨風險、交易降溫、應收到期與逾期及待辦事項；各項指標可下鑽至來源單據 |
| AI 營運摘要 | 後端先依固定規則計算指標，再由 AI 整理重要變化、可能原因、建議處理順序與來源連結 |
| LINE AI 建單 | 務在 Web 取得驗證碼完成本人綁定；AI 解析自然語言需求，提示缺漏或有疑義的欄位，並產生結構化預覽內容 ; 經業務確認後，系統才建立 SO 草稿 |

## 6. 系統中的角色

- 業務與業務主管。
- 採購與採購主管；小公司可由業務及業務主管兼任。
- 倉管與倉管主管。
- 財務與財務主管。
- 營運主管。
- 系統管理員。

詳細內容請查看 [04-roles-and-permissions.md](04-roles-and-permissions.md)。

## 7. 營運流程概覽

1. **接單**：收到客戶正式訂單後，業務以 Web 或 LINE AI 建立 SO。
2. **核准與預留**：主管核准 SO 後，系統預留現有庫存並標示缺料。
3. **缺料採購**（缺料時）：缺料轉為關聯 PO，入庫後補足訂單需求。
4. **出貨**：業務通知出貨，系統產生 DO，倉管交車過帳。
5. **應收**：系統依出貨產生應收，財務確認後登錄收款。

各步驟的角色分工、流程圖與例外處理，詳見  [02-business-processes.md](02-business-processes.md) 

## 8. 驗收標準

**核心資料流**
- 使用者能依授權登入、建立資料並完成指定核准流程。
- 一張測試 SO 能完整走過核准、庫存預留、缺料採購、入庫、出貨過帳、應收建立、部分收款及全額結清，並可在儀表板查閱對應的未收與到期狀態。
- 任一庫存數量都能追溯至入庫、預留、出庫或狀態異動紀錄。
- 主檔調價後，既有 SO、應收金額與歷史接單額皆不受影響。

**營運分析與 AI**
- 相同期間與篩選條件下，儀表板、明細與 AI 摘要的指標結果一致。
- 各項指標可下鑽至來源單據；一般使用者只能看到權限範圍內的資料。
- AI 摘要附上可查證的來源；資料不足時明確標示，不虛構結論。

**LINE AI**
- 未完成本人綁定或權限不足時，無法取得內部資料或呼叫 AI。
- 解析結果須經業務確認後，才建立 SO 草稿。
