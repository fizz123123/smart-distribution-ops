## 1. 文件責任

本文件回答「如何證明系統符合既定需求與規則」，集中記錄：

- 端到端驗收情境。
- 權限、狀態、例外與一致性案例。
- LINE AI、AI 營運摘要及外部服務失敗案例。
- 共用測試資料、驗收證據與整體通過標準。

[14-implementation-plan.md](14-implementation-plan.md) 僅描述實作順序、垂直切片與階段完成條件；領域規則、狀態與 API 契約仍以各自文件為準。若驗收案例與需求文件不一致，應先釐清並修正文件，不以測試案例自行改變需求。

## 2. 驗收原則

1. 每個案例必須能從畫面、API 回應、資料紀錄或來源單據觀察結果。
2. 同時驗證成功路徑與應被拒絕的路徑，不能只證明功能能操作。
3. 涉及庫存、預留、付款與單據狀態的命令，須驗證交易原子性。
4. 儀表板與 AI 使用的數字須能依固定公式重新計算，並可下鑽來源。
5. AI 驗收重點是輸入邊界、結構化輸出、來源驗證與失敗隔離，不以文句是否華麗判定。
6. 不以硬編碼結果代替測試資料；展示資料應能由可重現的初始化或操作流程建立。
7. 失敗案例不得留下部分成功、重複資料、錯誤庫存或錯誤金額。

## 3. 案例等級與結果

| 等級 | 定義 | 通過要求 |
|---|---|---|
| CRITICAL | 權限、交易完整性、庫存、預留、應收、付款與來源可信度 | 全數通過 |
| HIGH | 核心流程、例外處理、外部服務與跨模組交接 | 原則上全數通過；若調整範圍，須有決策紀錄 |
| NORMAL | 輔助查詢、操作便利性及非阻斷性呈現 | 不得存在阻礙主要展示的缺陷 |

案例結果使用 `NOT_RUN`、`PASSED`、`FAILED`、`BLOCKED`。`BLOCKED` 不視為通過，須記錄阻擋原因及後續處理。

## 4. 驗收環境與證據

驗收應至少區分：

- 本機或整合測試環境：執行自動化測試與錯誤情境。
- AWS 展示環境：驗證部署、HTTPS、S3 PDF、CORS 與外部整合。
- 固定測試資料版本：標示建立方式或資料版本，避免不同測試使用不同基準。

每筆驗收證據至少包含：

- 案例編號、日期、環境及執行者。
- 使用帳號與角色、測試資料版本。
- 操作步驟或自動化測試名稱。
- 預期結果、實際結果與結果狀態。
- 必要的畫面、API 回應、資料庫查核或紀錄片段。
- 問題編號及修正後重測結果。

證據不得保存密碼、JWT、OpenAI 金鑰、LINE Secret 或仍有效的 S3 Presigned URL。

### 5.2 客戶、商品與基準情境

| 代碼 | 設定 | 用途 |
|---|---|---|
| CUST_A | `NET_30` | 主端到端情境、部分收款 |
| CUST_B | `DUE_0` | 現結及多筆應收核銷 |
| CUST_COOLING | 至少 3 筆已核准 SO | 交易降溫分析 |
| ITEM_PE_PIPE | 基準單位「支」，可另設箱裝換算 | 單位換算及足量庫存 |
| ITEM_PU_SUPPORT | 基準單位「個」 | 缺料、採購與補足預留 |

主情境 `SO_MAIN` 使用以下固定資料：

- 客戶：`CUST_A`，付款條件 `NET_30`。
- PE 保溫管：可用庫存 10 支，未稅成交單價每支 100 元。
- PU 管墊：可用庫存 2 個，未稅成交單價每個 200 元。
- 訂購：PE 保溫管 10 支、PU 管墊 5 個。
- 未稅金額 2,000 元、稅額 100 元、含稅總額 2,100 元。
- SO 核准後預留 PE 10 支與 PU 2 個，PU 尚缺 3 個。
- 關聯 PO 合格入庫 PU 3 個後補足該 SO 預留。
- DO 過帳後產生一筆 2,100 元應收，分別收款 1,000 元及 1,100 元。

## 16. 主端到端驗收腳本

以 `SO_MAIN` 依序執行：

1. 業務由 Web 建立並送審 SO。
2. 業務主管核准 SO，系統預留現有庫存並顯示 PU 管墊短缺 3 個。
3. 採購建立關聯 PO 草稿，採購主管核准並取得正式 PO PDF。
4. 倉管依 PO 驗收 PU 管墊 3 個，合格入庫並補足來源 SO 預留。
5. 業務通知出貨並產生 DO 草稿，倉管確認實際數量後產生正式 DO PDF。
6. 倉管交車並執行出貨過帳，系統扣減庫存、使用預留並產生應收草稿。
7. 財務核對應收並填入外部發票號碼與日期，確認 2,100 元正式應收。
8. 財務先登錄 1,000 元部分收款，再登錄 1,100 元收清。
9. 營運主管查看儀表板，從出貨營收、缺貨與應收資料下鑽來源。
10. 營運主管產生 AI 營運摘要並驗證來源連結及資料權限。

此腳本通過時，須同時證明：

- 每一步只由具權限角色執行，且狀態順序正確。
- SO、PO、收貨、庫存、預留、DO、應收與付款數量及金額可勾稽。
- 失敗操作完整回滾，重複操作不產生重複異動。
- 儀表板與 AI 使用相同指標，且來源可追溯、受權限限制。

## 17. 整體通過條件

交付版本必須符合以下條件：

- 所有 CRITICAL 案例通過。
- HIGH 案例全數通過；未完成項目須經正式範圍決策並同步相關文件。
- 主端到端腳本可在固定資料下重複執行並得到相同結果。
- 不存在越權、資料洩漏、重複過帳、超額預留、錯誤金額或虛假來源。
- 庫存及預留一致性檢查通過。
- AWS 展示環境可由 HTTPS 使用，RDS 與 S3 維持非公開。
- PRD、流程、領域規則、狀態、API 與本驗收計畫內容一致。
- 驗收證據完整且不含敏感資訊。
